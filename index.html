RudderStack's Jev shadow test lost to its one-loop agent

Agents Web

RudderStack split a one-loop production agent into an evidence-gathering LLM step plus Jev decision calls. Jev itself did what it promised: under 0.1 seconds and about $0.00015 per decision. But over roughly 9,600 comparable real runs, the full shadow version took 7.2 seconds against 4.5 and cost $0.00411 against $0.00383, about 7% more. The evidence step cost about as much as the whole existing agent.

Why it matters: This is the useful decision-model production lesson: the final choice is often not the expensive part. About three-quarters of RudderStack's cost was reading context and tool results, so a typed judge pays when the evidence is already in the prompt, such as a final reviewer, not when another LLM must run the tool loop first. The post is honest about the remaining gap: it did not establish whether a tuned Jev chooses as well as the current agent.

vLLM shows NVMe can replace the DRAM KV tier

Craft Web

A vLLM/MoRI serving test put a 1.8TB agent KV pool on two local NVMe drives, using only about 80GB of DRAM for write buffering and read staging. On replayed Claude Code sessions, Kimi-K3 throughput stayed within 1% of a same-size DRAM pool at 48, 70 and 96 concurrent sessions. The argument is retention: Kimi-K3 wrote 2.3-4.6TB of KV an hour, so a 1.8TB pool held only 23-47 minutes regardless of medium, while NVMe makes longer retention cheaper.

Why it matters: For agent serving, throughput followed KV hit rate more than pool latency because asynchronous loads finished while requests waited for prefill. The actionable model is to size the pool from session pause times and write rate, not just buy the fastest memory. Caveats are explicit: tests used AMD MI355X nodes, Kimi-K3 and DeepSeek models with low KV per token, many key runs were single runs, and NVMe is unproven where the pool serves most prompt tokens.

KV-aware routing beats least-busy load balancing

Craft Web

Daily Dose of DS explains why the least-loaded model replica is not always fastest for agent traffic: another replica may already hold most of the prompt's KV cache. A KV-aware router scores both reusable prefix blocks and existing workload, tracks block hashes that include prior context, and avoids overloading the worker with the biggest cache match. The cited SGLang v0.4 shared-prefix benchmark raised cache hits from 20% to 75% and throughput from 82,665 to 158,596 tokens/s, about 1.9x.

Why it matters: For agents, stable instructions and tool definitions should sit before changing user or tool content so later calls can reuse prefill. If you serve replicas, compare least-connections, prefix-cache routing and cache-aware routing on the same traffic, and measure tail time-to-first-token as well as throughput. That 1.9x result came from a workload built around long shared prefixes, so do not assume it transfers to unrelated prompts.

Magnitude streams MoE experts from SSD to RAM

From production Web

Magnitude is an open-source local inference engine for sparse MoE models. It keeps shared layers and the most reused experts in GPU or unified memory, moves the next tier to RAM, and streams colder experts from NVMe SSD with prediction and prefetch. The project supports Apple Silicon, NVIDIA, AMD, Intel and CPU-only machines, exposes an OpenAI-compatible API and connects to coding agents. It is Apache 2.0 and says streaming weights is read-only, so it does not add flash wear.

Why it matters: This changes the local-serving question from “does the whole model fit in VRAM?” to “how well does the engine predict and cache experts?” Do not confuse active parameters with memory footprint: the full model still has to live somewhere, and VRAM must fit the active expert path. Benchmark TTFT, steady-state tokens/s, concurrency and NVMe speed before trusting demo numbers.

LMCache moves KV cache work out of the engine

Inference Apache 2.0

Today's Daily Dose deep dive revisits LMCache, an Apache 2.0 KV-cache management layer for production inference. LMCache runs cache movement outside the serving engine and tiers reusable KV state across GPU memory, CPU RAM, local SSD and remote backends such as Redis, Valkey, S3-compatible storage, NIXL and GDS. It is vendor-neutral, integrates with mainstream serving engines, and exposes Kubernetes and cache-level observability. The newsletter reports up to 14x faster TTFT in an H200 Qwen3-235B test; that number was not independently verified here.

Why it matters: Exact prefix caching breaks when document order changes or two cached documents are combined. LMCache's useful idea is architectural: move cache I/O off the inference critical path, share reusable state across engines, and degrade to ordinary inference if the cache process fails. Measure TTFT, hit rate, tail latency and recovery on your own prompts rather than trusting the headline speedup.

The companion recipe covers supervised fine-tuning followed by GRPO with verifiable rewards, plus a DFlash2 speculator. NVIDIA reports development score gains from 66.24 to 71.38, loop-flagged pages down from 126 to 29, and 7.62x faster concurrency-one parsing on one H200; those are vendor measurements.

Why it matters: Many RAG failures start before retrieval: tables lose structure, chart values are guessed, and headings disappear. This release gives you data and a recipe to specialize a parser for your own document shapes. Evaluate structural accuracy, numeric extraction, pages per second and downstream answer quality on representative PDFs before replacing your current OCR or parser.

GigaChat 4 releases a 708B MIT-licensed MoE

Open MIT

Sber's ai-sage team released GigaChat 4 708B-A41B under the MIT license, with FP8, BF16 and GGUF variants plus base checkpoints. The model combines 48 Gated DeltaNet layers with 16 sparse-attention MLA layers, supports a one-million-token context, and puts Instant and Reasoning modes in one instruction-tuned checkpoint. The technical report claims 71.26% on Terminal-Bench 2.0 in Reasoning mode, but its own table trails Mistral 4 Large, GLM-5.3 and DeepSeek 4.1 on Terminal-Bench 2.1 and DeepSWE.

Why it matters: This is a serious open-weight long-context release, not an automatic coding-model upgrade. Remember that 41B active parameters are compute per token, not memory footprint: all 708B weights still have to be stored and served. If you evaluate it, test long-document retrieval, tool use, reasoning latency, FP8 quality and the serving cost of the full checkpoint.

1Password traces a backend breach to a GitHub account

Security From production

1Password says an attacker used an employee's corporate GitHub account to read private source code, push malicious code into backend services, and copy account records for a subset of customers. Vault contents, account passwords and Secret Keys were not affected. The exposed records included names, sign-in emails, account metadata, and tokens in certain invitation or recovery links; the attacker also reached CI/CD systems containing infrastructure credentials. 1Password revoked access, rotated credentials, rebuilt affected services and lengthened recovery codes.

Why it matters: Agent-connected development pipelines make GitHub identity, CI permissions and deployment credentials part of the production attack surface. Audit who and what can push code, require deployment approvals, prefer short-lived scoped credentials, separate agent identities from human ones, and make sure repository access alone cannot silently change production.
