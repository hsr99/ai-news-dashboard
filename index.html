Pick of the week

Karpo Decision 31B opens a one-pass Jev-class model

Karpo Decision 31B is an open-weight multimodal decision model fine-tuned from Gemma 4 31B. It reads a state and typed questions over text, JSON and images, then returns every option probability in one forward pass without generating text. The Hugging Face card lists 31.3B BF16 weights, Apache-2.0 code and weights, a 62.5GB download, and a System One-compatible interface.

This is the week's most testable decision-model release: the Decision Index maintainers score it 73.9 Full, tied for first among 300 entries, and JevBench scores it 87.2, third among 243 Jev-class open-weight models. Karpo reports 95 ms median latency on one RTX PRO 6000, but long prompts can take seconds and the cost score is estimated from GPU time. Recalibrate thresholds on your own base rates; the release itself warns that fixed probabilities drift when deployment class balance changes.

Controlled study: small decision heads match 27M schemas

ResearchWeb

The Nov 13 paper re-implements five typed-decision readouts under one protocol: Qwen3-0.6B, 15 public English training sources, one recipe and one seed. Every head lands at 81.3-82.0% in-domain; a 0.5M-parameter cosine head matches a 27M-parameter joint-schema head in-domain at half its measured inference time. Joint prompts also match per-question prompts while running 1.6x faster at inference and 2.1-2.5x faster in training.

Why it matters: For a small decision model, the practical recipe is to spend effort on the backbone and keep the head minimal: moving to Qwen3-4B adds four points in-domain and eleven on held-out sources, while base, instruct and thinking checkpoints tie. The limits are clear: one seed, English data, single-H100 batch benchmarks rather than API latency, and no reverse-engineering of Jev's unpublished architecture or training data. The promised code repository was not publicly resolving when checked.

Treat inference-stack changes as model changes

CraftWeb

Acetrum's field note pulls together Ekka's catalogue of 90 real silent errors in vLLM and SGLang and a reproducibility study where backend choice alone shifted benchmark scores by up to 16.6 points. Its release rule is blunt: framework versions, quantisation, tensor parallelism, kernel backends, dtypes and cache settings all go through the same quality gate as a new model checkpoint.

Why it matters: The actionable gate is cheap: keep a boring reference configuration, replay a few hundred real production inputs, count exact answer disagreement before aggregate scores, record framework and backend details in every trace, and stop rollout when the quality delta crosses a preset margin. The 16.6-point swing is a worst cell in public benchmarks, not a universal rate, so verify your own workload. The primary Ekka and backend papers back the underlying risk.

Verify AI-generated PRs against acceptance criteria, not vibes

CraftWeb

Sonar's new verification guide lays out a usable pre-merge sequence: document what the change must do and what it may touch, inspect the diff for scope creep, invented APIs and unnecessary dependencies, run independent static, type, secret and dependency checks, map tests to acceptance criteria with negative cases, and require both contextual review and enforced branch protections. After fixes, rerun the full pipeline and keep the evidence with the PR.

Why it matters: The useful rule is separation of duties: an agent can self-check, but verification should use a different method from the one that wrote the code, and high-risk changes still need human approval. This is a vendor guide with a product pitch at the end, so skip the tool positioning and copy the checklist shape: requirements first, deterministic checks second, contextual review third, merge gates always. LeadDev's current report shows why this is urgent: 45% of surveyed engineering leaders now call code review capacity their biggest delivery bottleneck.

vLLM MonoKernels cut small-batch decode latency on AMD

CraftWeb

vLLM's FlyDSL MonoKernels combine dependent decode stages into a small number of persistent GPU launches on AMD Instinct hardware. The path is opt-in with --monokernel, keeps the stock scheduler, KV cache, speculative decoding and HIP graphs, and fails startup with reasons when the model or deployment is unsupported.

Why it matters: Decode sits on the critical path for interactive agents, and these kernels target exactly the low-concurrency case where per-user latency matters more than aggregate throughput. Merged PR evaluations report 1.20-2.26x concurrency-one interactivity gains across DeepSeek, MiniMax, Kimi and Muse configurations, with documented accuracy checks mostly within noise. The limits are explicit: gains narrow as concurrency rises, step widths are capped, boundaries are model-specific, and some older AMD parts need extra weight copies. Treat the numbers as per-model serving evidence, not a blanket vLLM speedup.

Two answers to harness drift: remember why, or train inside the harness

CraftWeb

Google's Self-Improvement Memory keeps a structured history of harness problems, edits, expected and observed outcomes so an optimizer can continue after a model or benchmark changes. In its paired coding test, SIM finished ahead in 9 of 10 continuations by an average 2.36 points. Hugging Face's harness adapters take the complementary route: train a LoRA inside the actual agent harness, taking Qwen3.8-27B from 39% to 55% pass@1 under pi while cutting average tokens from 2.9K to 1.5K.

Why it matters: A tuned agent harness is model-specific evidence, not a portable asset. Before a model upgrade, preserve why each prompt, check and tool rule exists, and rerun evals in the real harness; when the task distribution is stable, adapting a small model layer inside that harness can recover accuracy and cost. SIM's result is a preprint with no public implementation, and Hugging Face's gains are benchmark-specific, but the engineering pattern is clear: keep optimizer history, and test the model and harness as one system.

Abnormal runs 77,800 agent investigations a day on one harness

From productionWeb

Abnormal's production email classifiers averaged about 77,800 completed investigations a day from September 29 to October 28. Every agent runs in one Temporal-based harness that supplies model profiles, monitoring, evaluation and retries, while teams compose task-specific agents from a shared capability catalogue.

Why it matters: The scaling lessons are concrete: share capabilities rather than whole agents, deduplicate identical in-progress and completed investigations, use fallback model profiles, and give LLM inference separate enforced capacity so throttling does not block tools or delivery. The 2.1x and 3.5x throughput ratios compare execution volume with Kafka, not cost or efficiency, and the quality numbers are internal. The architecture is still a useful template for moving from a few agents to many teams sharing one platform.

Google previews semantic governance for agent tool calls

AgentsWeb

Semantic governance policies are in preview on Google's Gemini platform. Agent Gateway sends each proposed tool call to a policy engine before the agent can run it; an LLM judge checks the call against the conversation, plain-language business rules and the user's original intent, then allows it or replaces it with a denial.

Why it matters: This puts an action-level check outside the agent, where a prompt or retrieved document cannot rewrite it. Policies can cover tools or parameters, and Cloud Logging stores the verdict, rationale and token use. The limits matter: the judge is probabilistic, streamed responses are not evaluated, and Google recommends dry-run review plus IAM, Model Armor and anomaly detection as separate layers. Start with a small deny rule set and log verdicts before enforcing.
